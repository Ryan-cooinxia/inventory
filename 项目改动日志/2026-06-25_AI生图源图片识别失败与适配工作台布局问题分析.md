# AI 生图源图片识别失败与适配工作台布局问题分析

## 日期

2026-06-25

## 问题现象

测试商品：采集商品 `source_id=49`，神牛 XPro 系列无线引闪器。

页面出现以下问题：

1. 点击左侧“AI识别图片”后提示：`识别完成：0/24 张图片，提取 0 条事实`。
2. 点击“批量分析”后能够生成部分视觉识别记录，但“产品识别详情”和统一证据列表仍主要只有网页文本数据。
3. 重复分析后视觉识别记录持续增加，存在重复事实。
4. 产品识别详情面板位置异常，破坏 Bootstrap 三栏布局。
5. 页面在宽屏及浏览器缩放后内容区域过窄，右侧存在大量空白。
6. SKU 的“佳能版、尼康版、索尼版”等版本信息被放入颜色字段，语义不正确。

## 数据核对结果

- 来源图片：24 张。
- 图片都存在本地路径，例如：`uploads/source_media/49/T_1.jpg`、`C_1.jpg`。
- 启用的视觉模型：`qwen_vl / qwen3-vl-plus`。
- `ImageAnalysisJob` 已存在多条 `success` 记录。
- 当前已有 `ImageFact` 20 条。
- 当前 `ProductFactEvidence` 只有 13 条，全部为文本证据，图片证据为 0。

因此，问题不是模型完全不可用，而是两个识别入口及事实写入链路不一致。

## 根因分析

### P0-1：旧图片识别入口无法加载本地图片

页面按钮调用：

```text
POST /ozon/api/adaptation/<source_id>/analyze-images
```

该接口只执行：

```python
requests.get(m.source_url)
```

而当前图片 URL 是站内相对地址：

```text
/ozon/uploads/source_media/49/T_1.jpg
```

`requests` 无法直接请求缺少协议和主机的相对 URL，因此 24 张图片全部进入“无法下载图片”分支。

### P0-2：新识别服务无法把图片事实关联到 ProductFact

`services/vision_tool.py` 使用：

```python
ProductFact.source_id == media.source_id
```

但 `ProductFact` 不存在 `source_id`。真实关系是：

```text
ProductFact
→ SourceProductGroup
→ SourceProductGroupItem
→ OzonSource
```

结果是：

```text
模型调用成功
→ ImageAnalysisJob success
→ ImageFact 写入成功
→ 查找 ProductFact 报错
→ ProductFactEvidence 图片证据无法写入
```

### P0-3：异常被静默吞掉

`api_analyze_product_fact` 中使用：

```python
try:
    ...
except:
    pass
```

这会把数据关联错误隐藏掉，页面只看到识别数量不正确，无法看到具体失败原因。

### P0-4：系统同时保留两套图片识别流程

当前存在：

1. 旧流程：`api_analyze_images → call_vision_api`
2. 新流程：`api_analyze_product_fact → analyze_product_image`

两套流程在图片加载、Prompt、事实结构、任务日志和证据写入方面均不一致，造成：

- 同一个按钮和批量分析结果不同；
- 旧流程只写 `ImageFact`；
- 新流程计划写 `ProductFactEvidence`，但关联错误；
- 后续维护会继续出现行为漂移。

### P0-5：SKU 证据对象映射错误

视觉服务使用来源 SKU `OzonSourceSku` 作为 `ProductFactEvidence.fact_sku` 候选，但该外键要求 `ProductFactSku`。

应通过：

```text
ProductFactSku.source_sku_id == OzonSourceSku.id
```

或 `fact + source_order` 映射到正确的事实 SKU。

### P1-1：重复识别没有完整幂等控制

当前数据库已有同一批图片的多轮成功任务和重复 `ImageFact`。虽然证据层设计了 `evidence_hash`，但 `ImageFact` 和任务层没有按图片内容、模型、Prompt版本做幂等或修订管理。

### P1-2：页面 Bootstrap 网格结构错误

“产品识别详情”卡片被直接放在 `.row` 内，但没有任何 `col-*` 包裹：

```html
<div class="row">
  <div class="col-lg-3">...</div>
  <div class="card">产品识别详情</div>
  <div class="col-lg-5">...</div>
  <div class="col-lg-4">...</div>
</div>
```

Bootstrap `.row` 的直接子元素必须是列。当前结构会破坏 3+5+4 的十二列网格，引起面板错位、换行和宽度异常。

### P1-3：基础模板固定使用 `.container`

`base.html` 将全部页面包在固定最大宽度的 `.container` 中。适配工作台属于高密度工作台，宽屏下应使用 `.container-fluid`，否则浏览器缩放后会出现大量空白和内容过窄。

### P1-4：产品详情只是原始证据标签，不是聚合商品档案

当前面板直接按 `ProductFactEvidence.group_key` 显示若干 badge：

- 没有聚合同一事实的多条证据；
- 没有显示证据数量；
- 没有明确未知、冲突和完整度；
- 每组只显示前 5 条；
- 图片证据没有写入，因此实际只显示文本信息。

## 修复方案

### 第一阶段：统一图片识别服务（P0）

1. 删除或停用旧 `api_analyze_images` 内部识别实现。
2. 左侧“AI识别图片”和“批量分析”统一调用同一服务。
3. 统一使用 `services.vision_tool.analyze_product_image()`。
4. 图片加载顺序：
   - 优先 `media.local_path`；
   - 再处理站内相对 URL；
   - 最后请求公网 URL。
5. 视觉模型配置查询必须排除 `provider.startswith('img_gen_')`。
6. API 返回每张图片的成功、失败、错误原因和新增事实数，不能只返回总数。

### 第二阶段：修复事实关联（P0）

新增统一查找函数：

```python
resolve_fact_context(user, source, media=None)
```

通过 `SourceProductGroupItem` 查找 `ProductFact`，并将 `OzonSourceSku` 映射到 `ProductFactSku`。

禁止再访问不存在的 `ProductFact.source_id`。

图片识别成功后的原子处理顺序：

```text
ImageAnalysisJob
→ ImageFact
→ ProductFactEvidence
→ 聚合商品详情刷新
```

任何一步失败都记录任务错误，不得静默忽略。

### 第三阶段：幂等与批量处理（P0）

1. 识别全部 24 张图片，不使用固定 `.limit(10)`。
2. 采用分批执行，例如每批 5 张。
3. 任务指纹建议包含：
   - media_id；
   - 图片哈希；
   - 模型配置 ID；
   - Prompt 版本；
   - task_type。
4. 指纹相同且已有 success 时默认跳过；用户选择“重新识别”时创建 revision。
5. `ImageFact` 增加去重或以任务修订为边界展示。
6. 前端显示进度：`已处理 5/24，成功 4，失败 1`。

### 第四阶段：通用商品详情聚合（P0）

产品详情不能直接堆砌证据，应由服务层生成通用摘要：

```python
build_product_detail_summary(fact)
```

动态分组：

- identity
- sku
- structure
- specification
- function
- compatibility
- package
- selling_point
- usage_scenario
- target_customer
- safety
- certification
- custom
- unknown
- conflict

每个聚合事实返回：

```json
{
  "field_path": "compatibility.camera_brand",
  "label_cn": "适配品牌",
  "value": ["Canon"],
  "status": "extracted",
  "confidence": 0.93,
  "applicable_skus": [2],
  "evidence_ids": [31, 48],
  "evidence_count": 2,
  "source_types": ["image", "text"]
}
```

不能硬编码当前产品字段。没有预设字段时保存到 `custom`。

### 第五阶段：页面布局重构（P1）

在 `base.html` 增加可覆盖的容器类：

```jinja2
<div class="{% block container_class %}container{% endblock %}">
```

适配工作台覆盖为：

```jinja2
{% block container_class %}container-fluid px-3{% endblock %}
```

推荐布局：

```text
页面标题
└─ 主工作区 row
   ├─ 左侧 col-xl-3：源资料、SKU、图片、补图
   └─ 右侧 col-xl-9
      ├─ 产品详细情况（全宽）
      └─ nested row
         ├─ col-xl-7：商品事实确认
         └─ col-xl-5：OZON Listing
```

要求：

- `.row` 的直接子元素全部使用 `col-*`；
- 产品详细情况不再作为裸 `.card` 放入 `.row`；
- 原始证据列表和视觉结果放到折叠的“证据审计”区域；
- 产品详细情况作为主要业务视图；
- 不使用多个高度不足的嵌套滚动框；
- 在 1366、1600、1920 像素宽度以及 80%、100%、125% 缩放下检查布局。

## 验收标准

1. 24 张本地来源图片均能被读取。
2. 页面返回逐图识别结果，失败项有具体错误。
3. 图片识别结果同时写入 `ImageFact` 和 `ProductFactEvidence`。
4. 图片证据能出现在产品详细情况中。
5. 重复点击默认不产生重复事实。
6. 支持明确的“重新识别”修订操作。
7. SKU 版本不会再被强制写入颜色字段。
8. 产品详情支持不同品类和动态自定义属性。
9. 页面三栏/嵌套布局在宽屏下不出现大面积异常空白。
10. 所有异常均写入 `ImageAnalysisJob.error_message`，不得使用空 `except`。

## 本次状态

- 问题分析：已完成。
- 代码修复：未实施。
- 优先级：图片加载与事实关联为 P0；布局重构为 P1。

## 2026-06-26 复查：点击“AI识别图片”完全无反应

### 直接根因

`templates/ozon/adaptation_workspace.html` 中的整段 JavaScript 无法通过语法解析，导致页面加载时脚本整体终止，所有函数均未注册。

使用 JavaScript 语法检查后，第一处错误位于 `analyzeImages()`：

```javascript
function analyzeImages() {
  analyzeProductFacts();
  return false;
    });
}
```

其中多余的：

```javascript
});
```

导致：

```text
SyntaxError: Unexpected token ')'
```

因此点击按钮时，浏览器找不到可执行的 `analyzeImages()`。

### 第二处语法错误

即使删除第一处多余代码，`analyzeProductFacts()` 中仍使用了非法的多行单引号字符串：

```javascript
var msg = '分析完成:
'+
  '已处理: ...'
```

JavaScript 的单引号字符串不能直接跨行，这会继续造成：

```text
SyntaxError: Invalid or unexpected token
```

应改成模板字符串：

```javascript
const msg = [
  '分析完成',
  `已处理: ${processed}/${total}`,
  `模型调用: ${d.model_calls || 0}`,
  `历史回填: ${d.backfilled || 0}`,
  `跳过: ${d.skipped || 0}`,
  `失败: ${d.failed || 0}`,
  `新增网页证据: ${d.text_facts || 0}`,
  `新增图片证据: ${d.image_evidences || 0}`,
  `冲突: ${d.conflicts || 0}`,
].join('\n');
```

### 第三处前端可靠性问题

`analyzeProductFacts()` 使用：

```javascript
var btn = event.target;
```

但该函数由 `analyzeImages()` 间接调用时，不应该依赖浏览器隐式全局 `event`。

应明确传入按钮或按 ID 获取：

```javascript
function analyzeImages() {
  return analyzeProductFacts(document.getElementById('btnAnalyze'));
}

function analyzeProductFacts(btn) {
  btn = btn || document.getElementById('btnAnalyze');
}
```

### 后端仍存在的问题

`api_merge_fact()` 的路由装饰器和 `@login_required` 仍然缺失，调用“合并事实”会产生 404 或无法注册。

需要恢复：

```python
@ozon_bp.route('/api/product-fact/<int:fact_id>/merge', methods=['POST'])
@login_required
def api_merge_fact(fact_id):
```

`services/product_fact_service.py` 中仍残留不存在的：

```python
ProductFact.source_id
```

审核商品事实时仍有运行失败风险。

本次问题属于可在提交前自动发现的静态语法错误。后续每次修改模板 JavaScript 后必须执行：
